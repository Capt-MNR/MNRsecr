.
تقرير تدقيق وتصميم: Learning Loop للسكرتير الشخصي
تم إجراء التدقيق على الكود الحالي فقط. لم يتم تعديل كود الإنتاج أو مخطط قاعدة البيانات أو الواجهة أو الاختبارات.

الخلاصة التنفيذية
المشروع لديه حدود معمارية جيدة يمكن البناء عليها:

البيانات القانونية موجودة في جداول منظمة.
ذاكرة المحادثة منفصلة ومحدودة ومعلّمة بأنها غير مصدر قانوني.
كل الكتابات تمر بمسار موافقة durable.
عمليات الموافقة محمية من التكرار والتنفيذ المتزامن.
عزل المستخدم والـtenant موجود في معظم عمليات القراءة والكتابة.
حل الكيانات الحالي يتعامل مع التكرار والغموض بدل الاختيار العشوائي.
لكن لا توجد حاليًا طبقة تعلم للمستخدم:

لا توجد جداول aliases.
لا توجد provenance أو confidence أو learning signals.
لا توجد آلية Memory Commit Report.
لا توجد واجهة لعرض أو حذف ما تعلمه النظام.
تقييم NLU الحالي لا يختبر دورة التعلم فعلًا.
لا توجد domain باسم appointments حاليًا؛ الموجود هو reminders وcommitments.
التوصية الرئيسية
MUST: إضافة Learning/Normalization داخل PostgreSQL الحالي، وليس قاعدة بيانات منفصلة.

MUST: إبقاء التعلم منفصلًا عن Structured Memory في البداية، وعدم تحويل أي alias إلى حقيقة دائمة إلا عبر إشارة قوية ومصدر معروف.

MUST: جعل الطبقة الجديدة data-driven وconfidence-driven، وليست parser جديدًا يعتمد على مجموعة كبيرة من Regex.

MUST: تسجيل learning signal بعد نجاح العملية وموافقة المستخدم، وليس عند مجرد اقتراح النموذج أو وصول رسالة عادية.

DO NOT DO: اعتبار موافقة المستخدم على تسجيل مصروف موافقة تلقائية على alias دائم.

DO NOT DO: السماح للنموذج بإنشاء أو تعديل alias دائم مباشرة.

7. التفاعل مع Approval وLearning
المسار المقترح:

User request
  → interpretation
  → proposed record
  → pending approval
  → user approval
  → atomic claim
  → DB write
  → deterministic commit report
  → learning signal
الفرق الضروري
موافقة على السجل
تعني:

المستخدم وافق على تسجيل هذا المصروف بهذه البيانات.
تعليم alias صراحة
تعني:

المستخدم قرر أن "محمد بتاع المحجر" هو "محمد أحمد".
ليستا الشيء نفسه.

السياسة المقترحة
MUST:

approval يسجل learning signal عن صحة العملية.
approval لا يرقّي alias تلقائيًا إلى approved.
explicit teaching أو confirmation صريح هو المصدر الأقوى للترقية.
تعديل record بعد alias خاطئ يسجل correction signal.
rejection لا يمسح alias معتمدًا تلقائيًا، لكنه قد يخفض الثقة أو ينشئ conflict signal حسب السبب.
مثال
إذا قال المستخدم:

دفعت لمحمد بتاع المحجر 3000
ثم وافق على العملية، هذا يعني أن العملية صحيحة في هذه اللحظة. لا يعني بالضرورة أن المستخدم يريد حفظ “محمد بتاع المحجر” كاسم دائم.

إذا قال:

افتكر إن محمد بتاع المحجر هو محمد أحمد
فهذه إشارة تعليم صريحة ويمكن عرضها للتأكيد أو تخزينها وفق سياسة alias.
