أولًا: Instruction Audit

نريد تحليل الـ6,162 حرفًا تقريبًا من التعليمات العامة التي تدخل في كل request، ومعرفة أين توجد أكبر فرص تقليل الـinput tokens.

افحص النص الفعلي الذي يتم إرساله للـproviders، وليس نسخة مختصرة أو وصفًا له.

قسّم التعليمات إلى فئات واضحة:

A — Core / Always Required

تعليمات ضرورية في كل request للحفاظ على هوية وسلوك الـSecretary.

B — Routing / Tool Use

تعليمات متعلقة باختيار الأدوات، tool calling، final_response، وترتيب/قيود تنفيذ الأدوات.

C — Memory / Context

تعليمات Second Brain، Context Assembly، structured records، relationship context، temporal memory، ومصادر الحقيقة.

D — Agent / Action

تعليمات التنفيذ، approval، mutations، Agent Work، proactive behavior، notifications، وغيرها.

E — Safety / Security

تعليمات حماية البيانات، tenant isolation، prompt injection، منع التنفيذ غير المصرح به، إلخ.

F — Redundant / Duplicated

أي تعليمات تكرر نفس المعنى أو توجد بصيغ متعددة.

G — Conditional

تعليمات لا تحتاج أن تدخل كل request ويمكن نظريًا إرسالها فقط عندما يكون السياق أو نوع العملية يتطلبها.

H — Potentially Compressible

تعليمات صحيحة ومهمة ولكن صياغتها أطول من اللازم ويمكن ضغطها دون تغيير معناها أو مستوى الحماية.

---

لكل فئة أريد:

- النص/الأجزاء التي تنتمي إليها.
- character count.
- byte count.
- إن أمكن token count حقيقي.
- هل هي Always Required أم Conditional؟
- هل توجد duplicate/redundant instructions؟
- هل يمكن ضغطها؟
- مستوى خطورة حذفها أو ضغطها:
  - Low
  - Medium
  - High

ممنوع اختراع token counts.
إذا لم يتوفر tokenizer مطابق للprovider، استخدم character/byte measurements فقط وقل بوضوح إن token count غير مقاس.

ثانيًا: ابحث عن التكرار

افحص الـsystem/developer instructions بحثًا عن:

- نفس القاعدة مكتوبة أكثر من مرة.
- نفس القيد موجود في system + tool description.
- نفس مفهوم memory/context مكرر.
- نفس قواعد approval/action مكررة.
- نفس قواعد عدم الاختلاق أو عدم التنفيذ مكررة.
- تعليمات قد تكون inherited من مراحل قديمة ولم تعد ضرورية.

لكن:

لا تحذف أو تعدّل أي شيء الآن.

أريد فقط تحديد التكرارات المحتملة.

خامسًا: إصلاح Benchmark Classification فقط

الـToken Audit كشف مشكلة مهمة:

في الجولة الأخيرة، Groq أرجع "final_response" تحتوي فعليًا على الحقائق الثلاث المتوقعة، لكن نتيجة التشغيل النهائية صُنفت Error وعُرض نص عام.

افحص "real-provider-benchmark.ts" ومسار استخراج/تصنيف النتيجة.

المطلوب فقط:

1. تحديد لماذا تم تصنيف نتيجة Groq كـError رغم وجود final_response صحيحة.
2. تحديد هل المشكلة في:
   - parsing
   - tool-call handling
   - final_response extraction
   - benchmark assertion
   - timeout/state handling
   - أو شيء آخر.
3. أصلح الـbenchmark test logic فقط إذا كان الإصلاح واضحًا وآمنًا.

مهم:
لا تغيّر production behavior حتى تجعل الاختبار ينجح.

الـbenchmark يجب أن يفرق بوضوح بين:

- Provider/API failure
- Tool-call failure
- final_response parsing failure
- Benchmark assertion failure
- Correct provider response

ولا تعتبر أي نص عام fallback نجاحًا إذا كانت الـprovider response نفسها فشلت.
