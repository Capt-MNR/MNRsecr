أولًا: Phase 2 Hardening أثناء التنفيذ

قبل البدء في Phase 3، راجع التنفيذ الحالي فعليًا، وليس التقرير فقط.

1. Financial balance invariants

تأكد من أن:

- "financial_obligations.principal_amount_minor"
- settlement totals
- "outstanding_amount_minor"
- obligation status

متسقة دائمًا.

المطلوب:

- partial settlement صحيح.
- multiple settlements لنفس obligation صحيح.
- settlement لا يتجاوز المتبقي.
- cancellation/correction لا تترك outstanding غير صحيح.
- correction لا تنتج duplicate settlement.
- "settled" لا يمكن أن يكون لها outstanding > 0.
- "open" لا تتحول إلى settled بدون تغطية صحيحة.
- إذا كان "outstanding_amount_minor" مخزنًا، فيجب أن يكون له invariant واضح ومحمى، وليس مصدر حقيقة مستقل يمكن أن ينفصل عن settlement history.

إذا وجدت أن التصميم الحالي يسمح بانفصال balance عن settlement history، أصلح ذلك قبل Phase 3.

2. Currency integrity

راجع كل المسارات المتعلقة بـ:

- obligations
- payments
- settlements
- donations
- income/receivables
- payment_links

وتأكد أن:

- settlement لا يمكن أن يربط payment بعملة مختلفة عن obligation.
- أي financial relationship لها currency semantics واضحة.
- لا توجد conversion افتراضية أو implicit conversion.
- multi-currency محفوظ بدون فقدان للمعلومة.

أضف tests للحالات السلبية، وليس فقط happy path.

3. Approval lifecycle — مهم جدًا

راجع المشكلة التي ظهرت سابقًا:

أحيانًا أول رسالة من المستخدم يتم تفسيرها كأن هناك approval، لكن Approval UI لا يظهر، ويحتاج المستخدم لإرسال نفس الطلب مرة ثانية حتى يظهر.

المطلوب إصلاح architecture وليس workaround.

المسار الصحيح يجب أن يكون:

User Request
→ deterministic/LLM intent resolution
→ canonical validated action
→ write policy
→ pending operation persisted
→ response indicates pending approval
→ frontend receives pending operation
→ Approval UI appears
→ approve/reject
→ atomic mutation + activity event

يجب ألا يعتمد ظهور Approval UI على أن الـLLM "يتذكر" أن يعرض modal.

إذا كانت mutation تحتاج approval، يجب أن يكون وجود pending operation حالة server-side مؤكدة.

اختبر specifically:

1. first request فقط.
2. لا يوجد second request.
3. pending operation يتم إنشاؤها.
4. frontend يحصل عليها.
5. modal يظهر.
6. reject لا ينفذ mutation.
7. approve ينفذ mutation مرة واحدة فقط.
8. refresh لا ينشئ operation ثانية.
9. retry لا ينفذ mutation ثانية.
10. نفس operation لا يمكن approve مرتين.
11. operation تخص نفس tenant/user.
12. canonical args/operation hash لا يمكن تغييره بين request وapproval.

إذا كانت المشكلة موجودة، أصلحها قبل الانتقال.

4. Activity atomicity

تأكد أن كل financial mutation المهمة تعمل:

mutation + activity event

داخل نفس transaction.

اختبر failure injection:

- إذا mutation نجحت وactivity event فشل → rollback كامل.
- إذا transaction نجحت → mutation + activity event موجودان.
- correction كذلك.
- settlement كذلك.
- payment-link كذلك.

راجع أيضًا event metadata بحيث يمكن معرفة:

- actor
- operation/source
- entity
- correction إن كانت correction
- relevant financial relationship

بدون تخزين أسرار أو بيانات غير لازمة.

5. Correction + rowVersion

اختبر:

- stale rowVersion → reject.
- current rowVersion → update.
- correction لا تنشئ record جديد بدل تعديل القديم إلا إذا كان ذلك مقصودًا.
- correction لا تكسر settlement/payment relationships.
- correction تعيد حساب/تتحقق من balances عند الحاجة.
- concurrent updates لا تسمح بالـlost update.

ثانيًا: Phase 3 — Typed Relationships

بعد نجاح Phase 2 Hardening، نفّذ Phase 3 في نفس branch.

الهدف هو تحويل النظام إلى relational Personal Information Graph باستخدام PostgreSQL/Drizzle.

ممنوع استخدام Graph Database.

العلاقات المطلوبة

أضف typed relationships واضحة وقابلة للاستعلام بين:

People ↔ Projects

استخدم/طوّر:

"project_people"

بحيث يمكن معرفة:

- الشخص المرتبط بالمشروع
- المشروع المرتبط بالشخص
- role إن كان مناسبًا
- relationship metadata إن كانت مطلوبة

People ↔ Tasks

أضف junction مناسب مثل:

"task_people"

مع tenant ownership.

Projects ↔ Tasks

أضف:

"task_projects"

إذا كان الـtask يمكن أن يرتبط بأكثر من project.

إذا كان business rule الحالي يفرض project واحد فقط، حافظ على ذلك ولا تضف تعقيدًا بلا داعٍ.

Tasks ↔ Purposes

أضف:

"task_purposes"

إذا كان task يمكن أن يرتبط بأكثر من purpose.

Reminders

اربط reminder typed مع:

- people
- projects
- tasks

باستخدام junction tables عند الحاجة.

Commitments

اربط commitment مع:

- people
- projects
- purposes

مع الحفاظ مؤقتًا على "commitment.personId" للتوافق مع البيانات الحالية.

لا تحذف "personId" الآن.

Financial Graph

تأكد من العلاقات بين:

Person
Project
Purpose
Financial Party
Obligation
Payment
Settlement
Donation
Income/Receivable

بشكل typed وواضح.

لا تستخدم polymorphic relation كـsource of truth للبيانات المالية.

ثالثًا: Entity Detail / Related API

طوّر الـentity detail architecture بحيث تصبح العلاقات قابلة للاكتشاف.

نريد architecture شبيهة بـ:

"GET /api/entities/:entityType/:entityId"

ويكون الناتج conceptually:

entity
related
relationships
timeline
capabilities

مع الحفاظ على APIs الحالية.

لا تكسر:

- "/api/people/:id"
- "/api/projects/:id"
- existing records APIs
- generated clients

أضف endpoints المتخصصة فقط إذا كان ذلك أنظف وأكثر أمانًا.

Security

كل traversal يجب أن يبدأ بـ tenant/user authorization.

ممنوع أن يؤدي relationship traversal إلى كشف entity من tenant آخر.

لا تسمح للـLLM بإرسال tenant/user IDs.

---

رابعًا: Bounded Relationship Traversal

لا تبنِ graph traversal مفتوحًا.

الـdefault:

- depth = 1
- hard maximum للـnodes
- server-side joins
- pagination للعلاقات الكبيرة
- authorization قبل traversal

يمكن تجهيز architecture تسمح depth=2 لاحقًا، لكن لا نحتاج تنفيذ traversal عميق الآن.

---

خامسًا: Activity Timeline

تأكد أن الـtimeline يستطيع تجميع الأحداث المتعلقة بالـentity من خلال:

"activity_event_entities"

مثال:

Person → يظهر له:

- expense
- payment
- debt
- advance
- donation
- income
- task
- commitment
- correction

Project → نفس الفكرة حسب العلاقات.

Timeline يجب أن يكون bounded/paginated.

Entity Detail:

سابعًا: Data Integrity

استخدم:

- tenant_id
- owner_user_id
- foreign keys
- indexes للعلاقات والاستعلامات المتوقعة
- unique constraints حيث يلزم
- rowVersion للـmutable entities

إذا ظهرت حاجة إلى migration destructive أو تغيير semantics لبيانات موجودة، توقف وابلغني بدل اتخاذ القرار بنفسك.
