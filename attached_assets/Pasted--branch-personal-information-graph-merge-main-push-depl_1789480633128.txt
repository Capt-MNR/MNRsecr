Context & Relationship Intelligence

الهدف الرئيسي:

اجعل Personal AI Secretary أكثر ذكاءً في فهم واسترجاع واستخدام المعلومات الموجودة في الـPersonal Information Graph، بدون زيادة عدد LLM calls.

PostgreSQL + typed relationships + activity + deterministic services هي مصدر الحقيقة.

الـLLM يستخدم فقط السياق الضروري عندما يكون reasoning/language generation مطلوبًا.

2. Relationship-aware Context Retrieval

أنشئ طبقة deterministic مسؤولة عن بناء context مرتبط بالسؤال.

Conceptually:

User Request
→ identify relevant entities
→ retrieve bounded relationships
→ retrieve relevant financial/activity records
→ rank/filter context
→ produce compact structured context
→ LLM only if needed

لا ترسل graph كامل إلى LLM.

يجب أن يكون هناك حدود واضحة لـ:

- maximum entities
- maximum related records
- maximum timeline events
- maximum context size

واستخدم pagination/limits الموجودة بدل تحميل كل البيانات.

---

3. Entity Resolution

طوّر الـentity resolution الموجود حاليًا بحيث يستطيع ربط الإشارات الطبيعية بالكيانات الموجودة.

أمثلة:

"محمد"
"محمد أحمد"
"أبو أحمد"

إذا كان هناك أكثر من candidate:

لا تخمّن.

استخدم ambiguity handling الموجود.

إذا كان match واضحًا:

استخدم entity ID داخليًا بدل إعادة تمرير الاسم فقط.

يجب ألا يتم إرسال tenant/user IDs من الـLLM.

---

4. Context for Follow-up Questions

هذه نقطة أساسية.

اجعل النظام يستطيع الحفاظ على referents structured.

مثال:

User:
"محمد عليه كام؟"

System resolves:
Person = محمد
Financial Party = X

ثم:

User:
"طب والمشروع التاني؟"

يستطيع النظام فهم أن السؤال follow-up مرتبط بالسياق السابق.

مثال آخر:

User:
"دفعت 5000 لمحمد في مشروع المحجر"

ثم:

"طب زود عليهم 2000"

يجب أن يعرف النظام ما الذي يشير إليه "عليهم" إذا كان السياق واضحًا.

إذا كان غير واضح:

ask for clarification.

لا تستخدم LLM إضافي فقط لحل حالة يمكن حلها من conversation state + graph.

---

5. Deterministic Financial Answers

أنشئ/طوّر deterministic query paths للأسئلة المالية المتكررة.

مثل:

- محمد عليه كام؟
- أنا ليا كام عند محمد؟
- كام دفعت في مشروع X؟
- كام لسه مستحق؟
- إيه السلف المفتوحة؟
- إيه الديون المفتوحة؟
- إيه المدفوعات الأخيرة؟
- كام دخل متوقع؟
- كام تم تحصيله؟
- إيه التبرعات المرتبطة بشخص/مشروع؟
- إيه الالتزامات المتأخرة؟

الحسابات يجب أن تتم من database/domain rules.

لا تجعل LLM يقوم بالحساب المالي.

إذا كان السؤال يحتاج مجرد lookup/calculation:

لا تستدعِ LLM إضافيًا إذا كانت architecture الحالية تسمح بإجابة deterministic.

إذا احتاجت الإجابة صياغة طبيعية، يمكن استخدام الـexisting LLM response path بعد تجهيز compact result.

6. Relationship-aware Tool Selection

راجع tool selection الحالي.

بدل عرض عدد كبير من الأدوات للـLLM، استخدم deterministic routing حيث يكون ذلك آمنًا.

مثال:

Question clearly about:

- person financial status
- project expenses
- open obligations
- recent payments

يمكن توجيهها إلى narrow tool scope.

لا تعيد بناء Context Budgeter أو Decision Cache rejected designs إلا إذا وجدت evidence جديدًا يثبت الحاجة.

لا تعيد فتح أي token optimization audit تم رفضه سابقًا بدون دليل جديد.

7. Structured Context Contract

resolved_entities
relevant_relationships

financial_summary

uncertainties

لكن لا تلتزم بهذا الشكل حرفيًا إذا كان هناك design أفضل في codebase.

المهم أن يكون:

- deterministic
- bounded
- typed
- testable
- compact
- tenant-safe

ولا يحتوي بيانات غير مرتبطة بالسؤال.

8. Memory Integration

اربط conversation state بالـGraph بدون تحويل كل شيء إلى permanent memory.

فرق واضح بين:

Conversation Context
Structured Memory
Canonical Domain Data

مثال:

"محمد" في المحادثة الحالية يمكن أن يكون referent مؤقت.

لكن relationship:

محمد → مشروع المحجر

يجب أن تكون في canonical domain data إذا تم تسجيلها فعليًا.

لا تخزن كل كلام المستخدم كـmemory.

---

9. Activity-aware Context

استخدم activity timeline عند الحاجة.

مثال:

"إيه آخر حاجة حصلت مع محمد؟"

يمكن deterministic retrieval أن يجمع آخر relevant events.

لكن لا تحمل timeline كامل.

اعمل relevance + bounds.

---

10. Context Compression بدون LLM

لا تستخدم LLM لتلخيص context إذا كان من الممكن تكوين compact structured representation deterministic.

مثال:

بدل:

100 payment rows

يمكن بناء:

- count
- totals by currency
- latest N
- open obligations
- relevant projects

مع الاحتفاظ بالـIDs اللازمة للتنقل أو follow-up.
