Audit: إيه اللي MNRsecr محتاجه عشان يبقى Agent ينفذ فعلًا؟
1. الـAction Architecture — 🔴 أساسي
نحتاج abstraction موحدة:
User Request
    ↓
Agent Understand
    ↓
Action Plan
    ↓
Action Execution Layer
    ↓
Connector / Runtime
    ↓
Observation
    ↓
Verification
    ↓
Evidence
والـAgent ما يعرفش تفاصيل التنفيذ.
مثلاً:
send_message
create_spreadsheet
read_email
open_app
tap
type
search_web
upload_file
كلها capabilities، والتنفيذ يحصل تحتها.
المطلوب Audit:
هل عندنا abstraction مناسبة أصلًا؟
هل Tools الحالية ممكن تكون foundation؟
هل Action وTool محتاجين separation؟
هل الـAction لها lifecycle وID؟
هل كل Action قابلة للتتبع والـretry والـverification؟
2. Messaging — 🔴
دي من أول الحاجات اللي لازم تدخل production capability.
نحتاج:
Read
قراءة رسالة
معرفة sender
معرفة conversation
معرفة timestamp
attachment metadata
unread state
Write
compose
send
reply
forward
attachment
Safety
READ → ممكن بدون approval
DRAFT → بدون approval
SEND → approval حسب policy
DELETE → approval
والـAgent لازم يعرف هل الرسالة اتبعت فعلًا، مش يكتفي بأنه ضغط زر.
نقطة مهمة
WhatsApp مثلًا ممكن يتعامل معاه من API في بعض السيناريوهات، أو من Android UI في سيناريوهات أخرى. لذلك الـcapability لازم تكون مستقلة عن طريقة التنفيذ.

GitHub
لكن لازم نعملها Execution Runtime خاص بـMNRsecr، مش نخلي الـLLM يبعث أوامر Android مباشرة.
4. Observation System — 🔴
دي أهم من الـtap نفسه.
بعد كل Action محتاجين نعرف:
إيه اللي حصل؟
مثلاً:
tap(send_button)
        ↓
observe()
        ↓
message_status = sent
والـObservation ممكن تكون:
Accessibility tree
screenshot
app/package
visible text
UI state
API response
ونحتاج Observation IDs / freshness حتى ما نستخدمش screenshot قديم لتنفيذ action جديد.
وده pattern مستخدم في أنظمة Android-agent الحديثة لأن stale UI ممكن يؤدي لضغطات خاطئة. �
GitHub
5. Verification — 🔴
لازم قاعدة ثابتة:
Action executed ≠ Action succeeded
مثلاً:
send_message
مش معناها:
tap() succeeded
بل:
tap
↓
observe
↓
verify message appears as sent
↓
success
ولو verification فشل:
retry / recover / ask user
وده يتكامل مباشرة مع Agent Work وEvidence الموجودين عندنا.

15. Recovery Engine — 🔴
لأن العالم الخارجي messy.
ممكن:
التطبيق يقفل
UI يتغير
network يفصل
button مش موجود
login انتهى
permission تظهر
action timeout
app يرجع screen مختلفة
نحتاج:
Action failed
↓
Observe
↓
Classify
↓
Recover
↓
Retry safely
↓
Verify
مع idempotency عشان ما يبعتش نفس الرسالة مرتين.
16. Agent Work Worker / Crash Recovery — 🔴
وده عندنا أصلًا كجزء ناقص.
لازم الـExternal Action يعيش حتى لو API process مات.
Work
 ├── state
 ├── lease
 ├── checkpoint
 ├── current_action
 ├── attempt
 ├── observation
 ├── evidence
 └── recovery
والـmobile runtime يعرف يرجع يكمل.
17. Evidence — 🔴
كل عملية خارجية مهمة لازم نقدر نثبت نتيجتها.
مثلاً:
Action:
send_message

Evidence:
recipient = Mohamed
status = sent
timestamp = ...
message_id = ...
أو:
create_spreadsheet

Evidence:
file_id = ...
sheet = Expenses
rows_written = 37
verified = true
وده جزء قوي جدًا عندنا لأن Agent Work/Evidence موجودين بالفعل.

مش نخلي الـAgent يكتشف ده بعد ما يبدأ المهمة.
19. Security Boundaries — 🔴
خصوصًا لأننا بنتكلم عن Agent يتحكم في الموبايل.
نحتاج deny boundaries واضحة للـAgent:
Banking
Password managers
OTP
payment confirmation
system security settings
destructive actions
مش معناها إننا ممنوعين دائمًا؛ معناها إن الـruntime ما يتعاملش مع كل UI بنفس الثقة.
حتى Android agents الحالية تصطدم بقيود مثل FLAG_SECURE والشاشات المقفولة وبعض التطبيقات التي لا تعرض UI قابلًا للأتمتة. �
