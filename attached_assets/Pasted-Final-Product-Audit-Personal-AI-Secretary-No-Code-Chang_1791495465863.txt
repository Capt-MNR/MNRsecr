Final Product Audit — Personal AI Secretary

No Code Changes / No New Tasks

نفّذ مراجعة نهائية للمنتج الحالي فقط بعد اكتمال المراحل A–H.

هذه المراجعة ليست مرحلة تطوير جديدة، وليست طلبًا لإضافة features أو إعادة تصميم architecture.

قواعد إلزامية

- لا تعدّل أي ملف.
- لا تنشئ migrations.
- لا تضف components أو APIs أو routes.
- لا تغيّر backend contracts.
- لا تغيّر provider configuration أو AI models.
- لا تنشئ Replit tasks.
- لا تقترح backlog طويل.
- لا تعتبر وجود gap تلقائيًا عيبًا يحتاج implementation.
- راجع الكود والـUI والـflows الموجودة فعليًا فقط.
- لا تفترض capability لمجرد وجود schema أو type لها.
- لا تستخدم mock data أو fake connections أو fake Work كدليل على نجاح feature.
- إذا كان شيء غير قابل للتحقق من الكود/الاختبارات الحالية، قل بوضوح: غير قابل للتحقق حاليًا.

---

1. Audit من منظور مستخدم جديد

تخيّل مستخدمًا يفتح MNRsecr لأول مرة ولا يعرف أي شيء عن architecture أو backend.

قيّم:

خلال أول دقيقتين:

1. هل يفهم أن المنتج Personal AI Secretary وليس مجرد AI Chat؟
2. هل يفهم أين يتحدث مع السكرتير؟
3. هل يفهم أين يرى ما يحتاج منه؟
4. هل يفهم أين يرى الأشياء التي السكرتير يتابعها؟
5. هل يفهم أين يرى Context؟
6. هل يفهم أين توجد Connections؟
7. هل يستطيع اكتشاف طريقة واضحة ليقول للسكرتير:
   - اعمل حاجة
   - تابع حاجة
   - ذكّرني/راقب حاجة

أعطِ لكل نقطة:

- PASS
- PARTIAL
- FAIL

مع دليل مختصر من الـUI/code الحالي.

---

2. اختبر المنتج كـ Secretary Loop

راجع هل المنتج الحالي يوصل المستخدم منطقيًا إلى هذا التسلسل:

NOTICE → UNDERSTAND → SUGGEST → ASK/APPROVE → ACT → VERIFY → REMEMBER → FOLLOW UP

لا تفترض أن كل مرحلة يجب أن تكون مرئية دائمًا.

المطلوب تحديد:

- أين تبدأ كل مرحلة فعليًا؟
- أين تظهر للمستخدم؟
- هل الانتقال للمرحلة التالية مفهوم؟
- هل هناك نقطة يشعر عندها المستخدم أن النظام "اختفى"؟
- هل هناك مرحلة موجودة backend لكن غير مفهومة product-wise؟

ركز خصوصًا على:

Action lifecycle

هل المستخدم يستطيع فهم الفرق بين:

- pending approval
- executing
- verifying
- completed
- rejected
- expired
- failed
- unknown_result
- needs_review
- cancelled

وهل الـUI يتصرف بشكل صحيح مع كل حالة؟

---

3. Secretary → Ask → Context → Work

راجع الترابط بين الـ4 surfaces الأساسية:

Secretary

هل هو فعلًا Attention Engine وليس مجرد Dashboard؟

Ask

هل هو المكان الطبيعي لإعطاء السكرتير طلبًا؟

Context

هل يجيب فعليًا عن:

«"إيه اللي السكرتير يعرفه عن ده؟
إيه اللي حصل؟
إيه اللي بيتابعه؟
وإيه المطلوب؟"»

Work

هل يمثل الأشياء التي السكرتير يتابعها/ينفذها فعلًا، وليس مجرد قائمة database records؟

تحقق من navigation والـhandoffs بينهم.

خصوصًا:

- Secretary → Ask
- Secretary → Work
- Context → Ask
- Context → Follow
- Person → Ask/Follow
- Project → Ask/Follow
- Record → Context
- Quick → Main

---

4. Work Discoverability

راجع هل المستخدم يستطيع اكتشاف فكرة:

«"اجعل السكرتير يتابع"»

بدون أن يعرف مصطلح Agent Work أو workflow.

تحقق من وجودها في الأماكن الصحيحة التي أُضيفت في Phase D.

لكن لا تعتبر وجود زر وحده نجاحًا.

اسأل:

- هل wording مفهوم؟
- هل المستخدم يعرف ماذا سيحدث بعد الضغط؟
- هل السكرتير يأخذ الطلب الطبيعي؟
- هل clarification موجود فقط عندما يكون supported؟
- هل النظام يتجنب اختراع capability؟
- هل إنشاء Work يتم من خلال Agent وليس frontend direct POST؟
- هل "عرض المتابعة" يظهر فقط عند وجود Work حقيقي؟

---

5. Trust / Approval / Verification

راجع تجربة الثقة بالكامل.

اسأل:

قبل التنفيذ

هل المستخدم يعرف:

- ماذا سيحدث؟
- لماذا يحتاج approval؟
- أي service سيُستخدم؟
- هل approval مرتبط بالعملية نفسها؟

أثناء التنفيذ

هل الحالة واضحة؟

بعد التنفيذ

هل المنتج يفرق بين:

- action completed
- action failed
- result unknown

خصوصًا:

UNKNOWN_RESULT

يجب ألا يظهر للمستخدم كأنه:

- success
- normal failure
- شيء يمكن retry له تلقائيًا

ويجب أن يكون واضحًا أن هناك حاجة للمراجعة/التأكد.

راجع أيضًا:

- stale approval
- owner/tenant scoping
- operationId continuity
- Quick/Main handoff

---

6. Connections

راجع Connections كمفهوم product وليس مجرد صفحة settings.

هل المستخدم يستطيع فهم الفرق بين:

Connection
= الحساب/الخدمة المرتبطة

Capability
= ما يستطيع النظام فعله من خلال هذه الخدمة

Permission
= ما يحتاج موافقة المستخدم

Action
= العملية المحددة التي سيتم تنفيذها

تحقق أن الـUI لا يوحي بقدرات غير موجودة.

راجع Gmail / Calendar / Google Sheets بناءً على الـcontracts الحالية فقط.

لا تعتبر Google Sheets connected/ready إذا كان الـAPI لا يوفر هذه المعلومة.

---

7. Quick

راجع Quick باعتباره:

Interruption + Action Layer

وليس Mini Main.

تحقق:

- هل Quick سريع؟
- هل يعرض الحالة الحالية؟
- هل يستخدم نفس operationId؟
- هل approval/state مصدره backend؟
- هل يستطيع handoff إلى Main؟
- هل operationId ينتقل؟
- هل Main يعيد جلب الحالة الحالية؟
- هل unknown_result / needs_review يمنعان automatic approval/retry؟
- هل يوجد أي client-side execution أو polling أو duplicate execution path؟

ولا تقترح إضافة conversation list.

---

8. Context / Memory / Official Records

راجع authority hierarchy.

يجب أن تكون:

Structured / official records > inferred memory

تحقق أن Context لا يخترع:

- علاقة
- Memory
- Work relation
- provenance
- activity

فقط لأن أسماء entities متشابهة.

إذا لم يوجد typed/reliable relation في API، يجب أن يعامل النظام ذلك كـغير متاح، وليس كـinferred fact.

راجع progressive disclosure للـprovenance:

- original conversation إن وُجد
- record source
- activity
- memory
- work/evidence

ولا تفترض أن absence of provenance يعني manual creation.

---

9. Proactive Secretary Identity

راجع هل المنتج الحالي يوحي بأن السكرتير:

«"يتابع الأشياء معك"»

وليس فقط:

«"يجيب على أسئلتك."»

قيّم أمثلة مثل:

- approval يحتاج تدخل
- Work يحتاج review
- task overdue
- متابعة جارية
- notification بعد verification

ولا تقترح proactive features جديدة.

المطلوب فقط تقييم هل الـexisting product communicates هذه الهوية بوضوح.

---

10. Personality / User Preferences

راجع هل الـproduct architecture والـUX يسمحان بأن يكون سلوك السكرتير متكيفًا مع المستخدم:

- tone
- brevity
- formality
- notification behavior
- proactive behavior preferences

المطلوب ليس تنفيذ نظام Personality جديد.

فقط تحقق من عدم وجود UX أو architecture يجعل السكرتير يبدو كأنه يملك tone ثابتًا واحدًا لكل المستخدمين.

راجع المنتج باعتباره mobile-first.

تحقق من:

- Secretary

لا تقترح إعادة تصميم شامل.

13. Full User Journey

حاول تتبع هذا السيناريو منطقيًا من الـexisting product:

«مستخدم جديد يدخل التطبيق → يفهم أن لديه سكرتير → يسأل السكرتير عن شيء → يطلب منه متابعة شيء → إذا احتاج clarification يحصل عليه → إذا احتاج approval يظهر له بوضوح → ينفذ السكرتير → يتحقق من النتيجة → تظهر النتيجة → تستمر المتابعة إذا كانت العملية ongoing.»

لا تنشئ بيانات جديدة.

إذا كان جزء من السيناريو غير قابل للاختبار بسبب عدم وجود authenticated/live data، سجله كـ:

Not verifiable with current test environment

وليس FAIL.
