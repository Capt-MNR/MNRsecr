Frontend Integration & Interactive Secretary Experience — Full Phase

You are working on the existing "personal-information-graph" branch of the Personal AI Secretary project.

Your task is to complete the full frontend integration and interactive user experience for everything already implemented in the backend and intelligence layers.

This is one complete phase. Do not artificially split the work into separate phases unless you encounter a genuine architectural blocker.

You have autonomy over normal implementation decisions.

---

PRIMARY OBJECTIVE

The backend now contains substantial functionality that is not sufficiently visible or interactive in the current UI.

Your goal is to make the application visibly demonstrate the intelligence and Personal Information Graph we have already built.

The user should be able to open the application and immediately understand:

- who and what is connected
- what is happening
- what financial relationships exist
- what requires attention
- what actions are pending approval
- how people, projects, financial records, tasks, reminders and activity relate to each other

The result should feel like a Personal AI Secretary, not simply a collection of CRUD screens.

Do not build new backend intelligence unless it is strictly required to expose an existing capability through the UI.

3. MAKE THE PERSONAL INFORMATION GRAPH VISIBLE

The existing backend is structured as an interconnected information graph.

The frontend should make this relationship structure obvious.

Do NOT assume this requires a force-directed graph visualization.

Prefer a practical, highly usable interaction model:

- related entity cards
- relationship sections
- clickable entity chips
- contextual navigation
- expandable relationship groups
- timeline/activity connections

Example:

"Person → Project → Expense → Payment → Obligation"

or:

"Project → People → Expenses → Tasks → Commitments"

The user should be able to move naturally from one entity to another.

Every relationship displayed must correspond to real backend data.

Never create fake relationships merely for visual presentation.

8. APPROVAL EXPERIENCE — CRITICAL

Strengthen the existing approval UX.

Approval must be based on the server-side pending operation, not on the LLM response text.

If an operation requires approval, the frontend must reliably detect and display the pending operation.

The user should be able to understand:

What the secretary understood

Example:

«Muhammad paid 2,000 EGP.»

What will happen

«Record a payment of 2,000 EGP and apply it to the relevant obligation.»

What entities are involved

- Muhammad
- obligation
- project/purpose if applicable

Actions

- Confirm
- Reject / Cancel

The frontend must use the canonical server-side operation.

Never allow client-edited payloads to replace canonical operation arguments.

---

9. FIRST-REQUEST APPROVAL VISIBILITY

This is an explicit regression requirement.

Previously we observed a dangerous UX problem where:

1. The first request produced a response indicating that approval was needed.
2. The approval UI did not appear.
3. The user had to repeat the request.
4. The approval UI appeared on the second attempt.

This must NOT happen.

Verify that the first request can reliably surface the pending approval state.

The UI must not depend on the model remembering to emit a special UI instruction.

The server-side operation state is authoritative.

Test this explicitly.

14. DESIGN PRINCIPLE

The UI should answer the user's natural questions visually.

Instead of:

«"Here is a table of expenses."»

Prefer:

«"This expense belongs to this project, involves this person, was paid this way, and is part of this activity history."»

Instead of:

«"Here is a financial party."»

Prefer:

«"This person/entity is connected to these obligations, payments, projects and financial activities."»

The application should communicate relationships and context, not merely records.
