MNRsecr — Agent MVP 2.0

Personal AI Secretary → Personal AI Agent

0. IMPORTANT — READ BEFORE CHANGING ANYTHING

This is NOT a request to rebuild MNRsecr from scratch.

MNRsecr already contains substantial production architecture and working functionality.

The goal is to evolve the existing product into a true Personal AI Agent while preserving, integrating, and improving what already works.

Before implementation:

1. Audit the existing repository.
2. Understand the current architecture and data model.
3. Identify what already exists and what is missing.
4. Reuse existing systems wherever possible.
5. Do NOT create duplicate memory, provider, records, approval, or routing systems.
6. Do NOT remove working functionality just because the architecture is evolving.
7. Do NOT implement the entire vision at once.
8. First produce an implementation plan based on the actual current codebase.

The existing Second Brain is especially important and MUST NOT be rebuilt.

---

1. PRODUCT DIRECTION

MNRsecr is not primarily an AI chatbot.

It is a:

«Personal AI Secretary / Personal AI Agent»

The product should gradually evolve from:

«Remember → Understand»

into:

«Remember → Understand → Monitor → Act → Delegate → Anticipate»

and eventually:

«Learn → Repeat → Adapt → Improve»

The user should be able to give the agent a goal and leave.

Examples:

- "تابع سعر المنتج ده، ولو نزل عن 20 ألف بلغني."
- "كل يوم الساعة 9 راجع الموقع ده وشوف الطلبات الجديدة."
- "تابع المباراة وأول ما تبدأ عرفني."
- "لو الحجز فتح بلغني."
- "اعمل المهمة دي كل أسبوع."
- "عايز أعلمك الطريقة دي واعملها بعد كده لوحدك."

The core product hypothesis is:

«Users should be able to delegate useful real-world work to their personal secretary, not merely chat with it.»

3. SECOND BRAIN — FIRST-CLASS AGENT SUBSYSTEM

The existing Second Brain is an established subsystem.

It already includes concepts such as:

- second_brain_memories
- explicit save/retrieve
- provenance
- tenant/user scoping
- aliases
- search/retrieval
- archive/filter
- Retrieval Trace
- Candidate layer
- Policy Gates
- structured-record precedence
- alias safety
- review flows
- Web/Mobile management

DO NOT rebuild Second Brain.

DO NOT create another generic "Agent Memory" database that duplicates it.

Instead:

«Integrate Second Brain as a first-class cognitive/context subsystem of the Agent.»

The Agent should actively use Second Brain to reduce:

- repeated reasoning
- repeated context loading
- unnecessary LLM calls
- unnecessary tool calls
- prompt size
- token consumption

The architecture should conceptually be:

User
↓
Agent Brain
↓
Context Assembly
├── Second Brain
├── Structured Records
├── Conversation
├── Events
└── Current task/work state
↓
Agent Runtime
↓
Decision / Plan / Action

Second Brain is therefore not merely passive storage.

It is a source of already-known context that the Agent can exploit.

For example, when the user says:

"آخر حاجة حصلت مع شركة المحجر؟"

The Agent should not blindly send the entire database or conversation history to the LLM.

It should use:

- entity resolution
- Second Brain retrieval
- structured record retrieval
- provenance
- aliases
- recent relevant events

to assemble the smallest useful context.

- intent understanding
- context assembly

- decision making
- capability selection
- permission decisions
- execution
- verification

It should NOT duplicate Second Brain.

It should NOT duplicate Structured Records.

5. AGENT RUNTIME

The Agent must not be implemented only as:

Think → Tool → Think → Tool.

Introduce an explicit runtime/state model.

Suggested states:

CREATED
UNDERSTANDING
PLANNING
WAITING_PERMISSION
EXECUTING
VERIFYING
WAITING_EXTERNAL_EVENT
COMPLETED
FAILED
PAUSED

The actual implementation can differ if the existing architecture suggests a better approach.

The important requirement is:

«Agent work must be durable and resumable.»

A task that needs to wait for tomorrow, an external event, user approval, or a worker should not require the original HTTP request to remain alive.

6. AGENT WORK

Introduce the concept of an Agent Work / Job.

A user request that requires ongoing work should become a durable object.

Examples:

- Monitor product price
- Check website every morning
- Follow a sports event
- Monitor appointment availability
- Process recurring report
- Execute learned workflow

Agent Work should have:

- id
- owner
- goal
- current state
- creation time
- schedule if applicable
- trigger/event condition
- execution history
- latest result
- errors
- required permissions
- approval state
- workflow reference if applicable
- provenance
- timestamps

The user should be able to inspect what the agent is currently doing.

7. MONITORING ENGINE

Monitoring is a core MVP capability.

Do NOT implement monitoring as continuous LLM polling.

Prefer:

Deterministic check
↓
Did something change?
↓
No → stop
Yes → invoke Agent/LLM only if needed

Examples:

- price changed
- appointment became available
- match started
- task became due
- new email arrived
- order count changed
- workflow failed

The Monitoring Engine should support event-based conditions.

Potential events:

PRICE_CHANGED
MATCH_STARTED
TASK_DUE
EMAIL_RECEIVED
APPOINTMENT_AVAILABLE
USER_APPROVED
WORKFLOW_FAILED
DATA_CHANGED
SCHEDULE_TRIGGERED

10. TEACH ONCE → REPEAT

Introduce a learning/workflow capability.

User should eventually be able to say:

"عايز أعلمك حاجة تعملها كل يوم."

The Agent should learn a semantic workflow.

Example:

Open website
→ login
→ open orders
→ find new orders
→ summarize
→ notify user

Do NOT store workflows as brittle screen coordinates.

Store:

- user goal
- semantic steps
- required capabilities
- known integration/browser strategy
- expected result
- verification rules
- failure handling
- schedule
- user corrections

If a website changes, the Agent should be able to detect failure and request correction rather than silently continue incorrectly.

The long-term learning loop:

Teach
→ Execute
→ Observe
→ User correction
→ Update workflow
→ Repeat
→ Improve

For MVP, implement the smallest safe version of this loop.

---

11. EXECUTION LAYERS

When the Agent needs to act externally, use this priority:

1. Native API
2. Structured integration
3. Browser automation
4. Computer Use

Do not use Computer Use where an API is available.

Browser/Computer workers must be isolated from the main API process.

The system must verify execution results instead of assuming success.

Architecture:

Execute
↓
Verify
↓
Report

Never tell the user an external action succeeded unless there is evidence that it succeeded.

12. PERMISSION ENGINE

Agent autonomy must be controlled by explicit permissions.

Do not expose technical tool permissions to ordinary users.

Use human language.

Examples:

"أبعت الرسالة دي؟"

"أوافق إنك تعمل الحجز؟"

"تحب أستمر في متابعة السعر ده؟"

The system should distinguish between:

- already authorized
- confirmation required
- approval required
- prohibited
- expired permission

Use risk levels internally.

Possible levels:

LOW
MEDIUM
HIGH
CRITICAL

The exact classification should be determined from the actual actions.

Preserve the existing Main/Quick separation.

MAIN

It should eventually expose:

- conversation
- Agent Work
- monitoring
- records
- Second Brain
- Graph/Network
- approvals

14. TOKEN MINIMIZATION

Token minimization is a core architectural requirement.

Do not optimize by making the Agent less intelligent.

Optimize by preventing unnecessary LLM work.

Before calling an LLM:

1. Can this be deterministic?
2. Can an existing structured operation answer it?
3. Can Second Brain answer it?
4. Can a cached/known decision answer it?
5. Can a small classifier/extractor handle it?
6. Does the task actually require reasoning?
7. What is the smallest context needed?

The system should avoid:

- sending all tools every turn
- sending all conversation history
- sending irrelevant records
- repeating known context
- asking an expensive model to perform deterministic parsing
- repeated LLM calls for the same decision

Existing work such as:

- deterministic operations
- Entity Resolver
- Context Budgeter
- Local Router
- Decision Cache
- Provider Router

must first be audited.

Do not assume they are production-ready.

Determine which should be completed, modified, replaced, or deferred.

Build or evolve a dedicated Context Assembly layer.

Its job is to construct the minimum useful context for the Agent.

Potential sources:

- current user message
- recent conversation

- Structured Records
- Second Brain
- Graph relationships

- relevant events
- permissions
- user preferences

Context should be relevance-ranked and budgeted.

The Agent should not receive everything by default.

Second Brain retrieval should be one of the main mechanisms for achieving this.

28. WHAT THE MVP SHOULD ACTUALLY PROVE

The MVP does NOT need to prove that MNRsecr can do everything.

It needs to prove these four things:

1. Memory

The Agent genuinely remembers useful user context.

2. Delegation

The user can give it an ongoing job.

3. Monitoring

The Agent can wait and notice an event without being manually prompted.

4. Action

The Agent can perform at least some meaningful actions with permission.

If those four work well, we have a real Agent product foundation.

32. CRITICAL DESIGN PRINCIPLE

The Agent must not become an expensive LLM wrapper.

The architecture should be:

Deterministic when possible.
Second Brain when knowledge already exists.
Structured Records when data is structured.
Cheap models when simple reasoning is enough.
Core model when actual agent reasoning is required.
Deep reasoning only when justified.
External workers only when required.
LLM calls only when they add value.

The goal is:

«Maximum useful agency per token.»

FINAL PRODUCT GOAL

MNRsecr should evolve from:

«"An AI that I can talk to and that remembers me."»

into:

«"A personal secretary that knows my context, remembers what matters, watches things I care about, asks me when permission is needed, does work for me, learns how I want things done, and comes back when something happens."»

The mobile application is the user's primary control surface.

The Agent runtime and workers do the actual long-running work.

The Second Brain provides accumulated personal context.

Structured Records provide reliable facts.

The Agent Brain provides reasoning and orchestration.

Workers provide execution.

Monitoring provides awareness.

Permissions provide control.

Learning provides improvement.

And all of this must be designed around one core constraint:

«The agent should become more capable without requiring an LLM call for everything.»
