Product UX Completion — Interactive Personal AI Secretary

We are continuing on the existing branch:

"personal-information-graph"

The backend Personal Information Graph, Financial Graph, relationship layer, deterministic relationship-aware context, and the first frontend integration are already implemented.

However, the current frontend is technically connected to these capabilities but does not yet feel like a complete, interactive Personal AI Secretary product.

Your job is to take the current frontend from "connected screens" to a coherent, polished, interactive secretary experience.

IMPORTANT: WORK AS AN AUTONOMOUS PRODUCT + UX ENGINEER

Do not wait for me to specify individual UI components.

First inspect the existing frontend, routes, generated API clients, entity-detail pages, Records, Financial screens, conversation UI, approval UI, and the backend contracts they consume.

Then determine the best UX architecture for the product and implement the entire improvement in one pass.

Do NOT artificially split this work into multiple phases unless you genuinely become blocked by a technical or architectural constraint.

Do not ask me to choose colors, card layouts, component structure, navigation patterns, or other implementation details that can reasonably be decided from the existing product and conventions.

The goal is not "make the UI prettier."

The goal is:

«Make the user feel that this is a Personal AI Secretary with a living, interconnected information system behind it.»

---

1. PRODUCT EXPERIENCE PRINCIPLE

The product should communicate three things clearly:

A. The Secretary

The user should immediately understand:

- what needs attention
- what happened recently
- what is scheduled
- what financial activity occurred
- what is waiting for approval
- what people/projects need attention

B. The Personal Information Graph

The user should be able to move naturally through connected information:

Person → Project → Expense → Payment → Obligation → Person → Activity

and similarly in other directions.

The graph does NOT have to be a force-directed visualization.

In fact, do not introduce a complicated node/edge visualization unless you determine that it materially improves usability.

Prefer practical, touch-friendly, semantic relationship navigation.

C. Conversation

Conversation remains the primary way the user interacts with the secretary.

The structured graph should enhance the conversation rather than compete with it.

A user should be able to discover information through the UI and then continue asking the secretary about that information.

---

2. REDESIGN THE HOME EXPERIENCE

Audit the current Home page and transform it into a genuine Secretary Dashboard.

It should not feel like a generic admin dashboard.

It should prioritize attention and context.

Determine the best layout based on the existing application, but consider sections such as:

- Today / what's important
- pending approvals
- upcoming reminders
- tasks requiring attention
- recent financial activity
- obligations / advances / debts requiring attention
- recent payments
- receivables / expected income
- recent people
- active projects
- recent activity

Do not fabricate data.

Only display information supported by existing APIs.

The dashboard must gracefully handle:

- loading
- empty state
- partial data failure
- retry
- no financial data
- no tasks
- no reminders
- no pending approvals

Avoid turning the home page into an overcrowded wall of cards.

Use hierarchy and prioritization.

---

The current implementation allows users to open people/projects and see related records.

That is not enough.

The relationship system should become an actual interaction model.

When opening a Person, Project, or Financial Party, the user should immediately understand:

- what this entity is
- what it is connected to
- what activity happened recently
- what financial information is relevant
- what actions/navigation are available

Use appropriate grouped sections such as:

Person

- Expenses

- Tasks

- Financial relationships
- Recent activity

Project

- Purposes
- Recent activity

Financial Party

- Financial relationships
- People
- Projects
- Purposes
- Advances
- Debts
- Payments
- Receivables
- Donations
- Activity

Only show sections that have meaningful data.

---

4. BIDIRECTIONAL NAVIGATION

This is critical.

If:

Person → Project

exists, the user should be able to navigate from the person to the project and from the project back to the person.

Likewise:

Project → Expense

Expense → Project

Payment → Person / Project / Obligation

Obligation → Person / Project / Payment

Task → Person / Project / Purpose

Reminder → Task / Person / Project

etc., wherever the current backend relationships support it.

Do not invent relationships that do not exist.

Use the existing APIs and relationship contracts.

The user should feel that all of these are parts of one connected system rather than separate database screens.

---

5. ENTITY PAGES SHOULD BE ACTIONABLE

Entity detail pages should not become passive reports.

Where supported by existing functionality, make relevant items clickable.

Examples:

- clicking a person opens that person's detail
- clicking a project opens project detail
- clicking an expense opens the relevant record
- clicking a task opens its record
- clicking a reminder opens its record
- clicking a financial party opens Financial Party Detail
- clicking an activity item opens the underlying entity/record when possible

Preserve clear back navigation.

Deep links must continue to work.

Do not break existing Wouter routing.

---

6. TIMELINE / ACTIVITY EXPERIENCE

Improve the timeline so it feels like a useful history of the relationship/entity.

It should communicate events naturally.

For example:

- Expense recorded
- Payment made
- Obligation created
- Task created
- Reminder scheduled
- Relationship created
- Record corrected

Use the existing activity-event system.

Do not create another event source.

Do not expose internal database terminology unnecessarily.

Make events visually scannable and clickable where possible.

Preserve pagination and bounded reads.

---

7. RECORDS EXPERIENCE

Audit Records as part of the complete product flow.

Records should feel connected to the rest of the application rather than being a standalone database table.

Ensure:

- deep links work
- recordId opens the intended record
- related entity links are usable
- financial records lead to their relevant entity context
- deleted/unavailable records have a useful state
- loading/error/retry states are clear
- navigation back to conversation works
- existing editing/deletion/approval behavior is preserved

Do not remove existing functionality.

---

8. FINANCIAL EXPERIENCE

The Financial area must feel integrated into the Personal AI Secretary.

Keep the existing financial semantics exactly as implemented.

Do NOT introduce a generic "net balance" unless an explicitly supported existing backend calculation exists.

Preserve:

- currency
- direction
- lender/borrower semantics
- payer/payee semantics
- outstanding calculation
- settlement rules
- approval
- corrections
- row-version protections
- tenant isolation

Improve the UX around:

- advances
- debts
- payments
- settlements
- donations
- income / receivables
- financial parties

Make navigation between financial entities and their related people/projects/purposes obvious.

---

9. CONVERSATION + GRAPH INTEGRATION

This is one of the most important product requirements.

The user should be able to move between structured information and conversation naturally.

For example:

User opens a person.

From that page there should be an obvious way to continue asking the secretary about that person.

If the existing conversation/context mechanism supports entity context, use it.

Use the deterministic relationship-aware context already implemented.

Do NOT add new LLM calls simply to make the UI smarter.

Do NOT create a second memory system.

Do NOT duplicate backend relationship logic in the frontend.

Where useful, preserve the selected entity as navigation/context state using existing architecture.

---

10. APPROVAL UX

Keep the server-side pending operation as the authoritative source.

The frontend must never manufacture or modify the canonical operation.

The approval experience should make it obvious:

- what the secretary wants to do
- which entities are affected
- what amount/currency is involved where applicable
- what will happen after approval
- approve
- reject
- loading
- error
- already completed
- already rejected
- operation still processing

Most importantly:

The first request must be able to produce a visible approval experience.

Do not rely on the model response text to make approval appear.

The pending server-side operation is authoritative.

If the current architecture still has a path where the first request returns a pending operation but the UI fails to display the approval until the user repeats the request, identify and fix that path.

Preserve canonical operation arguments and idempotency.

Do not weaken security.

---

11. MOBILE-FIRST UX

The application must work as a serious mobile product.

Audit every major screen.

Pay special attention to:

- conversation
- dashboard
- entity details
- records
- financial screens
- approval forms
- navigation/drawers
- timelines
- relationship lists

Avoid horizontal overflow.

Make touch targets practical.

Keep important information visible without excessive scrolling.

Preserve the current mobile conversation drawer behavior and Escape handling.

---

12. VISUAL HIERARCHY

Do not simply add more cards.

Create a clear hierarchy.

The user should be able to answer quickly:

1. What needs my attention?
2. What happened recently?
3. What money-related things matter?
4. Who and what am I dealing with?
5. Where can I drill down?
6. How do I ask my secretary about this?

Use consistent visual patterns for:

- entities
- relationships
- financial records
- tasks
- reminders
- approvals
- activity
- navigation

Reuse the existing design system/components whenever possible.

Avoid introducing unnecessary dependencies.

---

13. LOADING / EMPTY / ERROR STATES

Every major data-driven section must have an intentional state for:

- loading
- empty
- error
- retry
- success

Empty states should explain what the user can do next where appropriate.

Avoid generic "No data" messages when a more useful explanation is possible.

Do not make the UI appear broken when the backend simply has no records.

---

14. DO NOT CHANGE THE BACKEND CONTRACT UNNECESSARILY

The existing backend and graph foundation are the result of previous architectural work.

Prefer consuming existing APIs.

Only modify backend code if a frontend experience genuinely cannot be implemented correctly with the current contracts.

If a backend change is required:

- keep it minimal
- preserve existing semantics
- preserve tenant isolation
- preserve approval
- preserve idempotency
- preserve bounded reads
- preserve financial correctness
- do not create a second source of truth

Do not add migrations unless genuinely necessary.

---

18. PRODUCT QUALITY BAR

Do not consider this task complete merely because:

- the pages render
- APIs return 200
- TypeScript passes
- the screens technically link to each other

The acceptance criterion is experiential:

«A new user should be able to open the application and understand that they have a secretary, see what matters, open a person/project/financial entity, explore its relationships naturally, drill into records, understand recent activity, return to conversation, and approve actions without feeling that they are navigating disconnected database screens.»

If the current UI architecture prevents this, improve the architecture within the existing frontend rather than layering more disconnected components on top.
