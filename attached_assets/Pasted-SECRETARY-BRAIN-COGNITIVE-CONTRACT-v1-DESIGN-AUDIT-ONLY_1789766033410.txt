SECRETARY BRAIN — COGNITIVE CONTRACT v1
DESIGN + AUDIT ONLY — DO NOT IMPLEMENT

We are now defining the cognitive contract for the Personal AI Secretary.

IMPORTANT:
This phase is architecture/design only.
Do NOT modify production behavior.
Do NOT add new tables.
Do NOT add new APIs.
Do NOT change prompts.
Do NOT change provider routing.
Do NOT optimize LLM usage.
Do NOT refactor existing deterministic intelligence.
Do NOT introduce an agent framework.

The goal is to define the Brain's responsibilities and boundaries before implementation.

==================================================
1. CORE DEFINITION
==================================================

The Secretary Brain is the decision layer between:

User / Event
      ↓
Secretary Brain
      ↓
Context + Memory + Structured Records
      ↓
Reasoning when needed
      ↓
Decision
      ↓
Action / Response
      ↓
Verification

The Brain is NOT the LLM.

LLMs are reasoning engines that the Brain may choose to use.

The Brain must be hybrid:
- deterministic rules
- structured state
- database/graph retrieval
- memory policies
- confidence/risk evaluation
- LLM reasoning when genuinely useful

Core principle:

"The Brain should use the least expensive reasoning strategy that preserves the required level of secretary intelligence."

This does NOT mean minimizing LLM calls blindly.

The product priority is:

INTELLIGENCE > COST OPTIMIZATION

while avoiding unnecessary reasoning.

==================================================
2. COGNITIVE PIPELINE
==================================================

Define the Brain conceptually as:

RECEIVE
→ UNDERSTAND
→ ASSESS
→ SELECT CONTEXT
→ REASON (when needed)
→ DECIDE
→ ACT / RESPOND
→ VERIFY

Not every request must pass through every stage.

Examples:

"دفعت لمحمد 500 جنيه"
→ understand
→ assess
→ deterministic action
→ approval
→ execute
→ verify

"فاكر آخر حاجة حصلت مع محمد؟"
→ understand
→ retrieve relevant memory/records
→ reason/summarize
→ respond

"أنا مسافر الأسبوع الجاي، ظبطلي التزاماتي"
→ understand
→ temporal interpretation
→ retrieve multiple domains
→ reason
→ produce plan
→ ask/confirm before actions

==================================================

Define the following intent classes:

- retrieval
- action
- correction
- planning
- analysis
- conversational

The design must explain:
- how intents are detected
- when multiple intents coexist
- how ambiguous intent is handled
- when the Brain should ask instead of guessing

Do not assume every user message is an action.

==================================================
5. ENTITY MODEL
==================================================

Recognize these entity categories:

- person
- project
- financial_party
- expense
- task
- reminder
- obligation
- payment
- purpose
- date
- period

The Brain must distinguish:

Mentioned entity
vs
Resolved entity
vs
Ambiguous entity

Never silently convert an ambiguous entity into a confirmed entity.

==================================================
6. SOURCE SELECTION POLICY
==================================================

Define source precedence.

For financial/operational facts:
    Structured Records

For confirmed personal knowledge:
    Second Brain

For aliases:
    Second Brain + Entity Graph

For current conversation:
    Conversation Context

For analysis/inference:
    Multiple authoritative sources + LLM reasoning when required

Critical rule:

Structured operational records are authoritative over personal memory.

Second Brain must NOT determine:
- financial amount
- payment status
- debt/advance outstanding amount
- operational date
- transaction status

Memory can provide context, but cannot override structured operational truth.

==================================================
7. CONTEXT SELECTION
==================================================

Context retrieval is a cognitive decision, not merely a token optimization mechanism.

The Brain should determine:

What do I know?
What do I not know?
What do I need to know?
Which source can provide it?
How much context is actually necessary?

Define context categories:

- current conversation
- recent conversation
- structured records
- entity graph
- second brain
- provenance
- temporal context

Context should be:
- relevant
- bounded
- source-aware
- traceable

Do not dump the entire database or memory into the LLM.

==================================================
8. INTELLIGENCE LEVELS
==================================================

Define four levels:

LEVEL 0 — DETERMINISTIC

Use for:
- obvious CRUD
- validation
- calculations
- approval
- known structured transformations
- explicit deterministic commands

No LLM required.

LEVEL 1 — LIGHTWEIGHT INTELLIGENCE

Use when:
- language is variable
- deterministic parser is uncertain
- simple extraction/classification is needed

Output must be structured and validated before execution.

LEVEL 2 — NORMAL REASONING

Use for:
- contextual questions
- cross-entity reasoning
- ambiguity resolution
- relationship understanding
- natural conversational responses
- combining multiple structured sources

LEVEL 3 — DEEP SECRETARY REASONING

Use for:
- complex personal synthesis
- planning
- multi-domain reasoning
- proactive recommendations/suggestions
- situations where the user should genuinely feel:
  "السكرتير فاهم الصورة الكبيرة"

The Brain chooses the minimum level that preserves the required intelligence.

==================================================
9. CONFIDENCE MODEL
==================================================

Define:

HIGH
→ answer or execute when policy permits

MEDIUM
→ qualify, verify, or ask a focused question

LOW
→ do not guess
→ request clarification or evidence

Confidence must not be based solely on LLM self-reported confidence.

It should consider:
- source authority
- entity resolution
- ambiguity
- completeness
- conflicting information
- operation risk
- provenance quality

==================================================
10. UNKNOWN / MISSING INFORMATION
==================================================

The Brain must explicitly distinguish:

KNOWN
UNKNOWN
REQUIRED
OPTIONAL

Example:

User:
"ادفع لمحمد المبلغ اللي اتفقنا عليه"

Known:
- person may be محمد
- action = payment

Unknown:
- exact amount
- exact agreement
- payment method

Required:
- amount
- recipient confirmation if ambiguous
- approval according to policy

The Brain must not hallucinate missing values.

==================================================
11. ACTION POLICY
==================================================

The LLM must NEVER directly mutate the database.

Action pipeline:

Decision
→ Validate
→ Permission Policy
→ Approval if required
→ Deterministic Execution
→ Transaction
→ Verification
→ Response

The Brain may decide WHAT should happen.

The deterministic action layer decides HOW the mutation safely happens.

==================================================
12. VERIFICATION
==================================================

The Brain must distinguish:

"I decided to do X"

from:

"X actually happened"

After an action, verification must confirm the actual operation/result before the Secretary claims success.

Example:

BAD:
"سجلت المصروف."

when execution failed.

GOOD:
"تم تسجيل المصروف."

only after successful execution and verification.

==================================================
13. CORRECTION INTELLIGENCE
==================================================

Corrections must be treated as part of the cognitive contract.

Examples:

"لا، كنت أقصد 750 بدل 500"

"محمد مش أحمد"

"ده كان الأسبوع اللي فات"

The Brain must determine whether this is:
- correction of an existing operation
- correction of conversational context
- new operation
- clarification

Avoid duplicate operations.

==================================================
14. TEMPORAL INTELLIGENCE
==================================================

The Brain must understand:

- today
- yesterday
- tomorrow
- this week
- last week
- next week
- this month
- last month
- relative dates
- deadlines
- recurring periods

Temporal interpretation must become structured state before execution.

Do not rely on the LLM alone for final date calculations.

==================================================
15. PROVENANCE
==================================================

Important facts and actions should remain traceable.

Conceptual chain:

Conversation
→ Turn
→ Decision
→ Operation
→ Record
→ Activity

When the Brain reasons from information, it should know where that information came from.

The Brain should be able to answer internally:

"Why do I believe this?"

without exposing internal reasoning traces to the user.

User-facing provenance should expose sources/results, not hidden chain-of-thought.

==================================================
16. MEMORY POLICY
==================================================

Source hierarchy:

1. Structured Record
2. User-confirmed Memory
3. Inferred/Candidate Memory
4. Conversation Context

Candidate memories must not silently influence decisions.

Explicit memory commands can create confirmed memory according to existing Second Brain policy.

Memory retrieval must remain:
- tenant scoped
- user scoped
- policy gated
- relevance gated
- traceable

Do not expand memory behavior in this phase.

==================================================
19. FAILURE MODES
==================================================

Document how the Brain behaves when:

- entity is ambiguous
- information conflicts
- required context is missing
- memory conflicts with structured records
- LLM output is malformed
- provider fails
- deterministic execution fails
- approval expires
- verification fails
- user changes their mind
- conversation context is insufficient

For every failure:
prefer explicit uncertainty over hallucination.

==================================================
20. WHAT THE BRAIN MUST NOT DO
==================================================

The Brain must NOT:

- own the database
- bypass approval
- bypass tenant isolation
- mutate records directly
- treat LLM output as truth
- treat memory as operational truth
- silently resolve ambiguous entities
- invent missing values
- claim an action succeeded without verification
- expose hidden chain-of-thought
- become a giant prompt
- become a replacement for the existing structured architecture
