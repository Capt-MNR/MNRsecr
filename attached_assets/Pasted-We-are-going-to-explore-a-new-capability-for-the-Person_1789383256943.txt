Goal

We want to investigate whether we can create a local intelligence layer that gradually learns the user's vocabulary, aliases, corrections, relationships and recurring interpretations.

The principle is:

LLM should NOT be the secretary's entire intelligence.

Instead:

User Data + Structured Memory + Normalization + Context Engine + Learned User Vocabulary + LLM when necessary

The system should become more useful over time without proportionally increasing LLM token consumption.

Core concept

We want to introduce, conceptually, a:

Secretary Context & Learning Engine

It would sit between the user request and the LLM/database.

Example:

User:
"دفعت لمحمد بتاع المحجر 3000"

The system may eventually know:

"محمد بتاع المحجر" → Person P27
"المحجر" → Project PR12
"دفعت" → financial outgoing / expense

If confidence is sufficiently high, the system can resolve these locally without asking the LLM to rediscover the same information every time.

However, the system MUST NOT become a giant regex/deterministic parser.

We explicitly want to avoid returning to the previous architecture where many natural-language rules were hard-coded.

The learning layer should primarily be DATA-driven and confidence-driven.

Learning examples

Example 1:

User:
"محمد بتاع المحجر"

System discovers two possible people.

User:
"أيوه محمد أحمد"

Potential learned mapping:

"محمد بتاع المحجر" → P27

Future use:

"دفعت لمحمد بتاع المحجر 3000"

should resolve the person locally if confidence is high.

Example 2:

User:
"المشروع التاني"

If the conversation context establishes that two projects were recently discussed and the user selects the second one, the system should be able to retain the resolved reference in conversation context.

Example 3:

User correction:

System:
"هل تقصد مشروع A؟"

User:
"لا، أقصد مشروع المحجر."

The correction should potentially become a learning signal, but NOT automatically become permanent truth unless the architecture provides a safe mechanism for validating/promoting it.

Very important distinction

We need to distinguish:

1. Permanent structured facts
2. Conversation-local context
3. Learned aliases/preferences
4. Temporary hypotheses
5. User corrections
6. Confidence scores
7. Provenance/source
8. User-approved knowledge

We do NOT want the system to blindly learn every sentence and eventually corrupt the user's memory.

Memory Commit Report

Investigate a mechanism called:

Memory Commit Report

Instead of sending the entire conversation to the real/structured memory layer, the conversation could produce a compact structured report containing only what materially changed.

Conceptually:

{
conversationId,
newFacts: [...],
updatedFacts: [...],
resolvedEntities: [...],
learnedAliases: [...],
corrections: [...],
contextUpdates: [...],
confidence: ...,
provenance: ...
}

The report should be small and structured.

IMPORTANT:
Do not assume the LLM must generate this report.
Investigate which parts can be generated deterministically from already-approved database operations and which parts genuinely require an LLM.

Approval integration

This is critical.

The user wants every action that changes user data to require permission.

Investigate how:

User request

Approval should be treated as a potentially strong learning signal, but distinguish:

"User approved this record"

from:

"User explicitly taught the system this alias."
