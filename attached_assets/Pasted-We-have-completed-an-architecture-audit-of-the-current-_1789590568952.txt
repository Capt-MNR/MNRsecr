We have completed an architecture audit of the current Personal AI Secretary implementation.

The current architecture is largely correct:

- Main Mode and Quick Chat use the same SecretaryChatService.
- Conversation continuity exists between Main and Quick.
- Operations, approvals, provenance, and structured records remain server-authoritative.
- There are extension points for channel/context/peer and future A2A.

However, the audit identified one important issue:

CRITICAL FINDING

Quick Chat is currently functionally lightweight, but it is NOT yet proven to be runtime/bundle/memory lightweight.

The current implementation places Main and Quick inside the same large frontend application/module tree and switches between them at runtime.

Therefore:

- "simpler UI" does NOT equal "lower RAM usage"
- deferred API queries do NOT equal "lower JavaScript memory"
- having fewer visible components does NOT equal "smaller loaded bundle"
- having a lightweight screen does NOT prove lower device RAM usage

Do not claim that Quick Chat is RAM-light unless this is actually implemented and measured.

We need to address this carefully without rewriting the application.

---

OBJECTIVE

Perform ONE final architecture-hardening pass covering TWO independent concerns:

A. Secretary Chat API boundary

Make Secretary Chat a clean, explicit backend capability shared by Main, Quick, Record/Entity Chat, and future external/A2A clients.

B. Real Quick Chat runtime separation

Make Quick Chat genuinely lightweight where the Expo/React Native architecture supports it, using code organization, deferred loading, and bounded data fetching.

The goal is NOT to create two different applications.

The goal is:

ONE Secretary
+
ONE backend
+
ONE conversation/operation/provenance system
+
TWO client experiences with different runtime loading characteristics.

---

PART A — SECRETARY CHAT API BOUNDARY

1. AUDIT CURRENT IMPLEMENTATION FIRST

Before modifying anything, identify the actual:

- SecretaryChatService
- HTTP chat/turn endpoint
- Main Mode chat client
- Quick Chat client
- Record/Entity contextual chat client
- conversation state
- turn creation
- operation creation
- approval flow
- provenance
- agentRuntime boundary

Do not assume filenames.

Preserve existing behavior unless a change is strictly required.

---

2. DEFINE AN EXPLICIT SECRETARY CHAT CONTRACT

Create a small typed server-side contract/interface.

It should conceptually support:

- conversationId
- message
- channel
- bounded context
- optional peer metadata
- stable turnId
- response
- operation/approval references where applicable

Do NOT expose database models.

Do NOT expose AgentRuntime internals.

Clients depend on Secretary Chat, not AgentRuntime.

---

3. MAKE THE HTTP CONTRACT REAL

The Secretary Chat HTTP endpoint must be capable of receiving:

- message
- conversationId
- channel
- bounded context
- optional peer metadata

Use the existing Zod/OpenAPI conventions.

Do not make optional concepts unnecessarily mandatory.

The important requirement is:

The HTTP boundary must not silently discard channel/context/peer information.

---

PART B — REAL QUICK CHAT LIGHTWEIGHT RUNTIME

This section is equally important.

4. CURRENT STATE MUST NOT BE MISREPRESENTED

Do NOT describe Quick Chat as "RAM optimized" merely because:

- it displays fewer components
- it fetches fewer APIs
- it has a smaller UI
- Main data is deferred

Those are useful optimizations, but they do not prove lower memory consumption.

---

5. SEPARATE QUICK AND MAIN MODULE TREES WHERE PRACTICAL

Refactor the frontend so that Quick Chat and Main Mode are separate screen/module boundaries.

The current large shared screen/module should NOT remain the place where the entire Main application and Quick Chat are defined together if that prevents effective deferred loading.

Target conceptually:

App Shell
├── Quick Chat entry
│   └── Quick Chat module
│       ├── conversation
│       ├── composer
│       ├── approvals
│       └── lightweight record links
│
└── Main entry
└── Main module
├── dashboard
├── records
├── people
├── projects
├── financial
├── tasks
├── reminders
├── activity
└── entity hubs

Do not duplicate Secretary Chat logic.

Only separate frontend loading boundaries.

---

6. USE REAL LAZY/DEFERRED LOADING WHERE EXPO/REACT NATIVE SUPPORTS IT

Determine what is actually supported by the project's Expo/React Native/Metro configuration.

Use the appropriate supported mechanism for:

- deferred module loading
- dynamic imports where supported
- route-level separation
- component-level lazy loading where supported
- code splitting if actually supported by the current build/runtime

Do NOT invent a web-only solution that does not work in native Expo.

Do NOT claim code splitting exists if Metro produces one runtime bundle in the current production configuration.

If true bundle splitting is not supported or not effective in this Expo setup, say so explicitly and implement the strongest practical alternative:

- separate modules
- deferred imports where supported
- route isolation
- avoid importing Main-only dependencies from Quick
- avoid mounting Main-only component trees
- avoid Main-only providers/query hooks in Quick

---

7. QUICK MUST NOT IMPORT MAIN-ONLY HEAVY MODULES UNNECESSARILY

Quick Chat should not eagerly import:

- Main dashboard
- Records workspace
- entity hub UI
- financial workspace
- large activity/timeline components
- Main-only visualization components
- Main-only navigation components

unless required when navigating from Quick into Main.

Do not duplicate these components.

Use navigation/deferred loading boundaries instead.

---

8. QUICK DATA FETCHING

Quick startup should only fetch what it needs.

At minimum:

- conversation state
- necessary Quick suggestions if enabled
- pending approval state when required
- minimal recent context if required

Do NOT automatically fetch:

- full records
- full people lists
- projects
- financial graph
- activity timeline
- dashboard aggregates

unless the user explicitly navigates to Main or requests them.

Existing bounded query behavior should remain intact.

---

9. PROVIDER / STATE ISOLATION

Quick should not initialize Main-only providers, subscriptions, or expensive state unnecessarily.

Audit:

- React Query observers
- navigation state
- dashboard hooks
- record hooks
- entity hooks
- activity hooks
- global listeners
- timers
- polling
- subscriptions

Quick should initialize only the state required for Quick.

Do NOT create a second global Secretary state system.

Conversation state must remain shared at the appropriate persistence/API level.

---

10. RAM CLAIM MUST BE MEASURED, NOT ASSUMED

This is critical.

After implementing the separation, do NOT say:

"Quick uses less RAM."

unless you actually have a measurement.

At minimum report:

Quick startup

- JS modules/components initialized
- API requests triggered
- active query observers
- mounted component count if measurable
- memory/RAM measurement if the environment exposes a reliable metric

Main startup

Same measurements.

Quick → Main

Measure what gets initialized after navigating from Quick to Main.

If device RAM cannot be measured reliably from the current Expo environment, explicitly report:

"Runtime RAM reduction could not be directly verified in this environment."

In that case, report the objective architectural evidence instead:

- imports separated
- Main modules not mounted
- Main queries not started
- Main-only providers not initialized
- deferred modules loaded only when entering Main

Do NOT convert those facts into an unsupported RAM percentage.
